# TB 填列实施计划：从「一种模板」到「各种试算平衡表」

更新于 2026-11-19。基于 `C:\Users\29294\Desktop\deeepaudit-训练文件` 的 181 个真实底稿与当前 0.8.1 代码实测。

## 一、先看清底数（实测，不是估计）

| 项目 | 结果 |
| --- | --- |
| 训练文件总量 | 181 个 xlsx |
| 单体 TB（45 表左右） | 79 个 |
| 合并汇总 TB | 8 个 |
| 合并抵消 TB | 7 个 |
| 附注 | 81 个（12 表左右） |
| 其他附件 | 6 个 |
| 单体样例识别结果 | **1012 个字段**（期初 506 审定 + 期末 506 账面），单位「元」自动识别，耗时 4.5 秒 |
| 合并样例识别结果 | **0 个字段**（按文件名含「合并/抵消」直接跳过） |
| 噪声警告 | 7 条，把「目录/封面/填表说明/现金流表」误报成「合并、抵消或期间标题存在冲突」 |

结论：**这 79 个单体 TB 今天就能填**，一次识别上千个字段、金额全部本地算。缺口不在「AI 够不够聪明」，而在模板形态与表头口径。

## 二、AI 在这条链路里的真实位置

现在的顺序（`gui._draft_tb` → `ai.tb_draft_batches` → `ai.review` → `matching.apply_ai_suggestions`）：

1. 扫表头，确定「哪一列是期末未审数 / 上期审定数」（`fields.scan_template`）
2. 行标签规范化：别名归并、`其中：`子行、`加/减` 前缀、投资性房地产/存货等特殊根（`matching._canonical`）
3. 规则匹配：一级科目取总额、父子不叠加、备抵科目按真实方向、应交税费/应付职工薪酬/未分配利润等专项（`matching.resolve_match`）
4. 本地算金额：方向、单位、期间、公式保护（金额从不交给模型）
5. **只有剩下 `ambiguous` / `unmatched` 的字段**才进模型，每批 ≤12 个，逐条过「候选白名单 + 父子算术守卫 + 本地重算」才可能被采纳
6. 人工在表格里勾选确认 → 写新副本 → 重算 → 导出核对表

所以：**规则决定能不能填对，Key 只决定「待确认」剩多少**。一个字段都没识别到时，配了 Key 也填不出来——这一点要先对齐，否则会误以为买 Key 就能解决模板问题。

## 三、现在就能用：操作设置（7 步）

1. **设置 → 模型设置**：粘贴 Key → 「连接并保存」（自动验 `/models` 与 JSON 能力）→ 先点「网络诊断」确认六段全通过。
2. **账套与 TB → 数据源**：安装目录（鼎信诺 `dnxservice`）→ 扫描项目 → 选主体 → 年度 / 截止月 → **读取科目余额**。
3. **模板与期间**：选模板文件 → 填列期间建议先用「仅期末」跑通 → 金额单位先留「自动」，不一致时会报错让你手选。
4. **先点「仅本地匹配」**：不花 token，先看规则能填多少（这部分最可信）。
5. **再点「AI 制作 TB」**：只把剩下的待确认字段发给模型，弹窗会显示发送范围与数量。
6. **看表格**：筛选切「需我处理」→ 逐条看「方法/原因」列 → 默认不覆盖模板已有值，要改的才勾「允许覆盖」→ 拿不准的用「指定来源」手工挑科目。
7. **导出核对表 → 另存 Excel**：核对表里每个字段都有「应填值/现有值/差额/来源科目」，先看差额再决定是否入表。

建议：第一次跑用一册没定稿的 TB，把「方法」列里 `exact`（编码或名称完全命中）和 `ai`（模型补配）分开统计，就知道规则覆盖率是多少。

## 四、各种模板今天能到哪一步

| 模板形态 | 现状 | 原因 |
| --- | --- | --- |
| 本所标准单体 TB（45 表，`试算平衡表(期初/期末)`） | ✅ 可填 | 列头「上期审定数/期末未审数」被 strict 模式精确命中 |
| 别家事务所单体 TB（表头写「期末余额」「期末数」「期末账面数」） | ⚠️ 识别不到 | strict 模式要求列头**完全等于**「期末未审数」，否则整表跳过 |
| 客户自制六列式（期初借/贷、本期借/贷、期末借/贷） | ⚠️ 待验证 | `_column_role` 有借贷方向分支，但未在真实六列模板上回归 |
| 合并汇总 TB（每列一个子公司） | ❌ 跳过 | 文件名含「合并」直接跳过；且语义是「汇总」不是「填列」 |
| 合并抵消 TB | ❌ 跳过 | 需要抵消分录数据，超出 TB 填列范围 |
| 附注（81 个文件） | ❌ 不做 | 属于附注产品线，不该混进 TB 填列 |

## 五、三条改造路线

| 路线 | 做法 | 成本 | 风险 |
| --- | --- | --- | --- |
| A 纯配置档案 | 每个模板族写一份 JSON（表名、表头行、列映射、单位、行标签列） | 低 | 换模板要手工写档案 |
| **B 配置 + 学习（推荐）** | 首次人工确认一册 → 固化为档案 → 同族模板自动套用 → 档案可导出给同事 | 中 | 需要一册"正确样例"作基准 |
| C 纯 AI 读表 | 每次让模型判断列含义 | 高（每次调用）、不可复现 | 审计上无法解释"凭什么这列是期末未审数" |

选 B。C 只作为「档案缺失时给一句建议」，绝不直接决定列位——否则同一份模板两次运行可能填到不同列。

## 六、分期落地

### P0（1–2 天）：让「别家模板」也能识别

1. `fields._column_role` + strict 匹配放宽为**同义词集合**：
   - 期末类：`期末未审数 / 期末余额 / 期末数 / 期末账面数 / 期末余额(账面)` 
   - 期初类：`上期审定数 / 期初余额 / 年初数 / 上年数 / 期初数`
   - 仍要求：同义集合内**唯一命中一列**，命中两列即报「存在多列目标金额，需要确认」，不猜。
2. 噪声警告降级：非 TB 页（目录/封面/填表说明）提示改为「非试算平衡表页，已略过」，只有真正的期间冲突才报错。
3. 单位/期间从表头第 3–4 行前置校验，避免 45 表里反复评估。

验收：把本所模板复制一份，把 `期末未审数` 改成 `期末余额`、`上期审定数` 改成 `期初余额`，仍应识别到 1012 个字段且列位一致。

### P1（3–5 天）：模板档案（核心）

4. 新增 `tb_autofill/profiles.py` + `tb_autofill/assets/template-profiles.json`：

```json
{
  "id": "zhongshen-huanqiu-single-v1",
  "name": "中审众环 单体 TB",
  "match": {"sheet": "^试算平衡表\\((期初|期末)\\)$", "header_keywords": ["报表项目", "索引号"]},
  "layout": {"header_row": 7, "label_cols": [1, 2], "index_col": 3},
  "columns": {
    "opening": {"audited": 4, "adjust_debit": 5, "adjust_credit": 6, "reclass_debit": 7,
                "reclass_credit": 8, "audited_final": 9, "client_reported": 10},
    "ending":  {"book": 4, "adjust_debit": 5, "adjust_credit": 6, "reclass_debit": 7,
                "reclass_credit": 8, "audited_final": 9, "client_reported": 10}
  },
  "unit": {"mode": "auto", "evidence": ["金额单位", "备注"]},
  "row_rules": {"section_headers": ["流动资产：", "非流动资产："], "skip_prefixes": ["加：", "减：", "其中："]}
}
```

5. 扫描优先级：**显式档案 > 自动识别 > 模型建议**。命中档案时不做 strict 猜测，直接按配置取列，并把档案 id 写进扫描结果（界面显示「模板档案：中审众环 单体 TB」）。
6. 界面：模板旁加「模板档案」下拉 + 「另存为档案 / 导入档案」，档案只存结构不存金额，可直接发给同事。

验收：同一份档案在 10 个不同主体的 45 表文件上，字段数与列位 100% 一致；换档案后差异只在行标签。

### P2（5–8 天）：多形态

7. **合并汇总 TB**：本质是「N 个单体同项目求和」，不是填列。建议先做**校验器**（汇总数 = Σ单体，差额逐项列出），再决定是否写回。改动点：`fields` 识别多实体列头（r6 公司名）+ 新 `matching.summarize()`。
8. **合并抵消 TB**：需要抵消分录，明确放在范围外，只做「抵消后 = 合并数」的勾稽检查。
9. **附注 81 个文件**：独立产品线，从 TB 填列流程中显式排除，避免误导入。
10. **六列科目余额表式 TB**：补 `period + side` 组合测试；这类表的「期末余额」本身带借贷方向，`matching._row_amount` 需按方向取绝对值。

## 七、规则库怎么扩（"自带规则"的真相）

现有规则（都在 `matching.py`，可增量扩，不必重写）：

- 别名组 `_ALIAS_GROUPS`：如「应收票据/应收款项融资」「固定资产清理」等归并
- 父子规则：一级科目取总账、有下级只列下级、父子不叠加（`_is_ancestor`）
- 备抵：累计折旧/摊销/减值准备按真实方向参与净额（`_asset_contra`）
- 专项：应交税费与增值税、应付职工薪酬、未分配利润跨期、投资性房地产计价模式、存货根集合

扩展方式（按性价比排序）：

1. **加别名**：`_ALIAS_GROUPS` 追加一行，立即生效，零风险。
2. **加专项钩子**：像 `_loan_component` 那样写一个 `_xxx(target, index)`，在 `_candidate_rows` 里注册。
3. **学习标签**：人工「指定来源」后，把 `(规范化行标签 → 科目编码集合)` 记进本地 `tb_learned.json`；下次同族模板优先命中。**只记标签与科目，不记金额**，金额每次从账套重算。
4. 不要做的：把金额、比率、结论写进规则或让模型算——这是现有设计的红线。

## 八、验收与回归（关键，不做这条就守不住）

- **Golden set**：5 个组各取 2 个主体，人工确认一次基准（脱敏：只留表名、表头行、行标签、列位、科目映射，不留金额），存 `tests/fixtures/profiles/`。
- 每次改动跑三件事：① 字段数一致 ② 列位一致 ③ 勾稽（资产 = 负债 + 权益）差额为 0。
- 现成的 `…-TB填列-…-待处理.csv` 可作真实回归基线，对比「应填值」变化。
- 现有 727 项测试必须全绿；新增 profile 与同义词用例。

## 九、风险

- 同义词放宽会把「调整前/调整后」误认成目标列——已由「调整/重分类/差额/客户报出」排除词兜住，但要补测试。
- 合并 TB 用单体流程硬套会得出「科目对不上」的假结论，必须在界面明确区分。
- 单位（元/千元/万元）混用只能人工确认，自动猜会让整册金额差 1000 倍。
- 档案本身是配置，不是证据；档案错了会稳定地错，所以每次换模板要人工核一次列位。

## 十、建议的下一步

先做 P0（同义词 + 噪声警告），1–2 天就能让「别家事务所模板」进入可用状态，风险最低、收益最直接；紧接着 P1 的档案机制，把「每次靠猜」变成「一次确认、长期复用」。
