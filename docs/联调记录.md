### 真实调用中的行为观察

用合成科目与 4 个目标字段（含同名歧义、币种限定、汇总行）请求复核，AI 返回空建议并给出拒绝理由：

> 「其他」存在多个同名候选（管理费用/其他、财务费用/其他），仅凭名称无法确定科目路径，不建议匹配；
> 「银行存款（美元）」在候选中仅有「银行存款」总账科目，无美元明细，名称不能证明对应关系，不建议匹配。

第二次以「房租租金支出」对「管理费用/房租」「销售费用/租金」请求复核，同样返回空建议（目标未标明父科目）。

这符合需求「名称不能证明时不建议匹配」。AI 建议被采纳的分支（选择来源后由本地重算金额、拒绝公式列与范围外科目）由 `tests/test_ai.py` 的离线用例覆盖，尚未取得真实接口下产生非空建议的样本。

### 审计专属通道实测

用真实接口验证「只做审计对话」是否真的成立（本地先判 + 模型判定双保险）：

| 输入 | 本地判定 | 模型判定 | 结果 |
|---|---|---|---|
| 帮我写一首关于秋天的诗 | offtopic | —（未发请求） | 本地拦截，不消耗额度 |
| 给我推荐几部电影 | unknown | offtopic | 模型拒绝，提案 0 条 |
| 帮我写个爬虫代码 | unknown | offtopic | 模型拒绝，提案 0 条 |
| 帮我总结一下这篇文章 | unknown | offtopic | 模型拒绝，提案 0 条 |
| 本期管理费用比上期增加 40%，可能有哪些原因？ | audit | audit | 正常作答（列出人工成本、折旧摊销等方向） |

实现要点：`audit_scope()` 本地先判（在题内放行、明确离题直接拒绝、模糊交给模型），模型返回 `intent=offtopic` 时**提案一律作废**；提案仍需人工确认并走 `resolve_match` 才能落盘。

排错记录：首版对话请求返回 `HTTP 400 请求格式不被模型支持`，原因是 `response_format={"type":"json_object"}` 要求提示词文本中出现 "json" 字样，而对话系统提示词未写；补上「只返回 JSON 对象」后恢复正常。

### 账套变动分析的接地性实测

真实账套（270 个科目，2021 年 12 月）生成事实清单后请求解释，结果：

| 指标 | 结果 |
|---|---|
| 事实条目（变动前 40 项，实际有变动 11 项） | 11 |
| 回答长度 | 1111 字 |
| 回答中引用但事实里没有的金额 | 0 |
| 回答中引用但账套里没有的科目编码 | 0 |
| 判定 | 通过 |

过程中发现并修复的三个真实缺陷：

1. **科目编码是 `5001.01.01.01.01` 这种多级点号结构**，原先只按 4 位纯数字识别，导致编码被误判为金额、父级编码识别不到。改为按"多级点号"匹配并对编码区间整体跳过。
2. **事实清单只给 Top12 太窄**，AI 引用清单外科目时无从核对。改为 Top40，并附上全部 270 个科目编码作为"编码白名单"——引用真实编码放行，编造编码报警。
3. **科目名称内嵌数字被误报**（如"农业银行43128"的账号尾号）。补充"名称/路径内嵌数字"白名单。

| 渠道 | 结果 |

| `git push`（代码与文档） | 正常 |

| GitHub Releases 制品上传 | **不可用** |

实测证据：`uploads.github.com` 被本地代理解析到 `198.18.112.226`（`198.18.0.0/15` 为保留测试段），连接 2.5 ms 即返回 302；24 MB EXE 上传 6 分钟后返回 `HTTP 408 Upload body timed out due to inactivity`；直接用 curl 访问该主机返回 `000`（无法建立连接）。改用阿里 DNS(223.5.5.5) 与腾讯 DNS(119.29.29.29) 查询，返回的仍是同一保留地址，说明 DNS 在本地被统一劫持，无法取得真实地址。

## 六、性能

反馈「换模板重新识别匹配太慢」后实测定位：慢在**匹配**而非模板识别。

测试条件：模板 404 行 × 10 列（800 个字段，17 KB），科目 2000 条。

| 环节 | 优化前 | 优化后 |
|---|---|---|
| `scan_template` | 60–86 ms | 60 ms |
| `match_fields` | **60,734 ms** | **116–139 ms** |
| 合计 | 约 60.8 s | 约 0.14 s（约 467×） |

**根因**：`_detail_label` 对每个目标都执行一次 `sorted(rows, key=lambda r: len(normalize(r.name)))`，`_candidate_rows` 又逐行重复计算规范化名称与集合，形成「目标数 × 科目数」的全量排序与正则重复计算。

**改动**：新增 `_Index`，一次性构建 canonic 名称 / 路径 / 叶子 / 精确名四类字典与按长度排序的前缀候选表；`normalize` 与 `_canonical` 加 `lru_cache`。逐目标只做字典查找，语义未变（61 项测试全绿）。

界面侧同步改进：更换模板后若科目余额已读取则自动重算，无需再点「识别并匹配」；日志与状态栏显示实际耗时。

新增回归用例 `ScalingTests`（400 目标 × 1000 科目，阈值 5 秒），防止退回逐目标全量排序。
